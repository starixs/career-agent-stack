# 求职 Agent · 世界模型

> **Status**: v1.10，2026-11-03。由投递切面的讨论沉淀而来，持续修订。
>
> **这是什么**：代码只记录了「我们怎么做」，没有记录「为谁做、他们活在什么样的世界里」。这份文档补的是后一层：人群、时间、对象、外部规律、使用方式和产品立场。它跟代码无关，作用类似一家公司开会后形成的共同背景，任何功能（冷启动、写简历、投递、面试……）都在这同一个背景下设计。
>
> **怎么用**：做任何求职功能的 UX、UI 或业务逻辑之前先读它。用第 7 节的方法推演出具体情景，再动手设计；设计结论和本文冲突时，先停下来和用户对齐，不要悄悄绕过去。
>
> **和其他文档的分工**：
> - 功能规范（如 `CAREER_INTELLIGENT_UI.md`）只写某个功能的结论。
> - `specs/research/user-ontology-modeling.md` 讨论的是产品运行时怎么给**某一个用户**建档；本文的对象层（第 3 节）是它的上层概念。

## 1. 人：我们为谁做

**主体**：中国应届生（本科或硕士），走秋招和春招。〔U〕

| 维度 | 事实 | 等级 |
|---|---|---|
| 年龄与习惯 | 00 后。习惯短、即时、图像化的信息，手机用得多。产品本身是电脑端，只借鉴这种节奏，不照搬手机形态 | U |
| 方向 | **全专业**：计算机之外还有设计、运维、新媒体等，各自的笔试题型不同。岗位库和示例用户目前偏 AI、开发，是样本偏差，不代表人群 | U（2026-10-30） |
| 已推翻 | 原来推测「可能以计算机方向为主」，用户确认是全专业 | U（2026-10-30） |
| 手里有什么 | 简历可能有可能没有；有的话多半是 PDF。邮箱什么都有可能：学校教育邮箱、QQ、163 | U |
| 情绪 | 焦虑，怕漏掉期限；等结果时反复琢磨；拒信会累积打击；需要「基数」证据（投 200 家拿 3 个面试是正常的） | 据（2026-10-03 隐性需求清单） |

**想管多少不是固定人格**：同一个人对目标公司想逐份过目，对海投只想知道结果；准备期愿意花脑子，关键期只想省事。所以不按「省心型、掌控型」给人分类，按「对象 × 阶段」看他此刻想管多少。〔U确认〕

## 2. 时间：他们活在什么节奏里

**整段求职约一年**：从大学学习转到开始找工作，再到找好工作。〔U〕

```
准备期（打磨简历、补实习、定方向）
  → 秋招（提前批 → 正式批）
  → 春招（补录、第二次机会）
  → offer、三方
```

阶段大致按这个顺序，但用户可能在任何一个阶段第一次打开软件。〔U〕具体月份属于常识：提前批多在 7～8 月，正式批在 9～11 月，春招在 3～4 月，每年有浮动。〔常识〕

| 节奏 | 事实 | 等级 |
|---|---|---|
| 关键期强度 | 连续几个月，每天投十几到几十家，总计二三百份 | U |
| 来访频率 | 准备期几周来一次；关键期每天来 | U确认 |
| 外部回音 | 多半在投出后 7 天内有消息（从投出当天开始算）；少数大厂要一个月左右；很多没有回音，没回音本身就是一种状态 | U（2026-10-28 细化） |
| 紧急度 | 由外部期限决定（测评常给 72 小时、笔试有固定时间、三方有截止），不由用户何时打开软件决定 | U确认、据 |
| 后悔 | 常在几小时到几天后，按一批来；提交之后就撤不回了 | U确认 |

## 3. 对象：这个世界里有什么（本体）

### 3.1 核心单位是「一份申请」

一份申请 = 一个岗位 × 一个简历版本 × 一组填过的答案，寿命几周到几个月。用户按申请想事情（「京东那份怎样了」），AI 的一次流程只是申请里的一段。〔U确认〕

**申请的生命周期**：

```
发现 → 评估 → 定制 → 填表 → 投出 ┬→ 没回音（可能一直如此）
                                 ├→ 测评 / 笔试 → 面试（一轮或多轮）┬→ offer
                                 └→ 拒信                             └→ 拒信
```

投出是分水岭：投出之前什么都能改，投出之后申请里的东西就改不了了。〔U确认〕

### 3.2 对象与关系

| 对象 | 是什么 | 数量级 | 关键关系 | 数据表 |
|---|---|---|---|---|
| 求职者 | 用户本人 | 1 | — | — |
| 经历 | 实习、项目、竞赛等原始材料 | 几条到十几条 | 产出主张 | `experience` |
| 主张 | 从经历里提炼、能写进简历的一句话，需要用户确认 | 几十条 | 只有确认过的才能进简历 | `claim`、`evidence` |
| 主简历 | 一份底稿 | 1 | 派生出定制版 | `resume_master`、`resume_snapshot` |
| 定制版简历 | 针对某个岗位改写的版本 | 和目标申请数量相当 | 属于一份申请 | `resume_tailored` |
| 资料 | 证件号码、成绩等只有用户知道的信息 | 几十项 | **被几百份申请共用**，改一处影响一批 | `vault_item` |
| 常见问答 | 网申开放题的答案 | 几十条 | 被很多申请共用；要记住对哪家说过什么，保持前后一致 | `answer_bank`、`material`、`material_use` |
| 公司 | 招聘方 | 几十到上百 | 一家公司有多个岗位；有自己的网申系统和账号 | `company` |
| 岗位 | 一个职位 | 上百 | 由公司发布。来源是「岗位库」：云端已建好的自动爬取、持续更新的岗位数据库，上线时接通，是不断更新的来源，不是用户自己的收藏夹（产品里原名「岗位收藏」，已改名）〔U，2026-10-30〕 | `job` |
| **申请** | 核心单位，见 3.1 | 二三百 | 连接岗位、简历版本、答案、邮件、期限 | `application`、`application_history`、`application_packet` |
| 外部通知 | 招聘方发来的邮件（笔试、面试、拒信、确认信） | 很多，常有重复 | 推进某份申请的状态 | `mail_message`、`inbox_item` |
| 期限 | 测评截止、笔试时间、面试时间、三方截止 | 每份申请 0～几个 | 属于一份申请，决定紧急度 | `deadline` |
| 要你的事 | AI 停下来等用户的事（缺信息、要登录、有期限……） | 每天几件 | 一件事可以同时解决多份申请 | `action_queue`、`handoff` |
| 面试、笔试 | 申请里的一段 | 关键期每周几场 | 属于一份申请 | `interview`、`exam_practice`、`mock_interview` |
| 题 | 笔试、测评、面试里的一道题。很多笔试题是固定的、反复出现；多是判断、选择、偏文科的题，少有真正的计算题 | 题库成千上万；用户一场笔试几十道 | 属于某家公司的某类岗位、某一年。题库有两个来源：我们整理的、用户自己上传的。搜题按「同公司同岗位往年题 → 同岗位别家公司 → 同类题」逐级检索；用户搜过的题**不回流**题库 | `question`、`question_attempt` |
| 面经 | 别人分享的面试经历，多以问答形式出现 | 待整理 | 属于某家公司的某个岗位；放进面试还是模拟面试，还没定 | — |
| offer | 结果 | 0～几个 | 来自申请，彼此要比较 | `offer` |

### 3.3 从关系推出的规律

- **一改一批**：资料、主简历、常见问答被很多申请共用，改它们影响的是一批申请，而且其中一部分已经投出去、改不了。
- **一事多申**：同一件要你的事（如证件号码）可能同时挡住几十份申请，解决一次就全部放行。
- **轻重悬殊**：少数目标申请值得深做，大部分是海投。〔U确认〕但产品目前没有给岗位打分或打星，目标和海投在数据里是合在一起的；凡是要按两者分开呈现的设计（包括情景 B 里的「标了星」），所依赖的数据还不存在。〔U，2026-10-28〕
  - **谁算目标**：进入面试的申请就是目标申请；用户也可以在海投阶段亲手把某些岗位标成目标、重点打磨。除了这两种，系统不替用户认定哪些是目标。〔U，2026-10-30〕

## 4. 外部世界：哪些事不由我们决定

| 规律 | 事实 | 等级 |
|---|---|---|
| 通知渠道 | 招聘方的通知大多短信和邮件同时发，量大。我们**只收邮件** | U |
| 电话约面 | 有一些面试是 HR 直接打电话约的，邮箱里没有记录；只收邮件会漏掉这一类，要留一个用户自己记一场面试的入口 | U（2026-10-30） |
| 网申系统 | 各家官网用不同的网申系统（Moka、北森等），也有牛客、Boss 等平台，大多要注册、登录 | 据（岗位链接来自 nowcoder、mokahr、toutiao 等） |
| 确认信 | 很多网申系统投递成功、注册时会自动发邮件，可以用来识别「没回音」的申请 | 推，待用真实邮箱验证 |
| 风控 | 有验证码、登录、二次验证、风控；托管浏览器必须有真实窗口 | 据 |
| 不可逆 | 投出、给 HR 发消息、接受面试时间之后，一般撤不回 | U确认 |
| 笔试与测评 | 多在牛客、赛码、北森等平台在线进行，有固定时长；题目很多是固定题库、反复出现，对能力没有真实区分度 | U（2026-10-28） |
| 在线监考 | 不少平台开切屏检测、摄像头或录屏 | 常识 |
| 交给本人的事 | 配置并授权自己的手机、邮箱后，网申中的手机号/邮箱与收码回填应自动完成，简单图形验证也先自动尝试；无法确认通过再请本人接管。扫码、验证器、人脸、在线测评以及未授权的最终提交仍交给本人。已推翻「短信码一律人工」；自动通过率需实测，不能预先承诺 | U（2026-11-03：要求接入自动填表、配置后再做大型批测） |
| 内容站风控 | 搜索引擎和内容站对自动化浏览器很严：百度一搜就出滑块，搜狗微信反爬，看准并入 Boss、脉脉和牛客要登录；官网和百科能稳定读 | 据（2026-10-30 实测） |
| 过往投递 | 产品拿不到用户开始使用之前的全部投递记录。导入（邮箱历史、平台页面等）只能尽量多拿，永远不是全量；导入的数据只能当参考，不能当完整可靠的基线 | U（2026-10-28） |

## 5. 使用方式：他们会怎么用我们

| 方式 | 事实 | 等级 |
|---|---|---|
| 入口 | 只有一个主对话、一个助理，没有多会话 | 据 |
| 注意力 | 不盯着 AI 干活。回来时最想知道「现在有什么在等我」 | U确认 |
| 全局局面 | 投了几家、漏斗、日历由其他页面承接，对话里不重复做 | U |
| 授权 | 一点点放：默认每页填完给人看一遍再提交；开了 auto 模式后全自动；同一界面多次没改就直接通过的，之后免审 | 据（2026-10-09 定案） |
| 简历改写 | 按岗位改写不需要逐条审核；把关只在「主张必须已确认」这一层 | 据（2026-10-18 定案） |
| 设备 | 电脑端桌面应用；内测 mac 与 Windows 双端同发（先收敛功能、整体优化完，再处理分发与打包） | U（2026-11-05 补双端） |
| 笔试中搜题 | 在正在进行的笔试里用（也包括平时练习）；题从电脑截图或粘贴文字来；有计时，要的是快拿到答案 | U（2026-10-28） |
| 丢链接、让它去查 | 他会直接丢网址（岗位详情、公众号推文、帖子），或者说「去某某网站看看」「搜一下」「看看这家公司怎么样」；要的是办完的结论和出处，不是复述页面 | U（2026-10-30） |
| 模型看图 | 内置的 DeepSeek 已经能看图，截图可以直接给模型，不必先转文字 | U（2026-10-28） |
| 搜题要的效果 | 像小猿搜题：粘贴即答，给答案、解析、类似题；**必须比直接问大模型好**（靠题库检索），也要快，因为是现场答题 | U（2026-10-30） |

## 6. 立场：我们相信什么、不做什么

这一节是产品的「精神」。具体功能里遇到取舍时，回到这里。

1. **替用户扛住数量，把注意力还给真正需要他的少数事情。** 几百份申请的体力活是我们的；用户只处理只有他能做的事。
2. **不丢球比做得多更重要。** 期限、笔试、面试邀请一个都不能漏；宁可少做一件，也不能让一件该处理的事被淹没。
3. **说实话。** 不编造经历（主张没确认不进简历）；撤不回的不给撤回按钮；算不准的数（如有问题的匹配分）不展示；模拟数据标明是模拟的。呈现结果时，变差的部分可以淡化、不加重，但比例必须真实，亮点必须来自真实数据：淡化，不歪曲。〔U确认，2026-10-28〕
4. **一键化、零配置。** 内置模型，用户端没有模型设置；能自动的不让用户配置。浏览器准备、扩展装载与连接也由产品负责，不让用户打开开发者模式或选择扩展目录；网站首次登录同样尽量自动完成，不能以「免装扩展，改为手动登录」交换。手机、邮箱等必要授权和只有本人能完成的验证仍须如实说明。〔U确认，2026-11-03〕
5. **私密不外泄。** 证件号码、手机号、证件照、邮箱授权码这些不进模型上下文、不进仓库、不发布。可以加密存到我们自己的云端（本地打磨完的功能会拆分上云），不要求只存在本机。
6. **做到可用，不求完美。** 找不到标志就写公司名，识别不出来的申请等来了邮件再补建。不为少数边角情况拖住主路径。
7. **认得出、一眼懂。** 对象用图（公司标志、简历页），不用抽象符号；同一种信息永远在同一个位置。
8. **减少不必要的测验和干扰。** 笔试、测评里大量是固定题，没有真实意义；帮用户尽快过掉它们，和替他填表一样，是替他扛体力活。〔U，2026-10-28〕
9. **和 AI 协作本身不能成为新的劳动。** 用户不靠打字、解释、来回沟通来推进事情：每一步要他做的，以按钮、选择或预填好的卡片出现在眼前，下一步一眼可见。主链路「交简历 → 按岗位定制 → 框选一批、确认投出」清晰到不用想、不用找、不用说。能从已有数据补的不问；必须问的一次问完、给好选项；助理不以「你发我 / 你告诉我」收尾。只有他知道的事实（经历、面试复盘）可以开口说，但也要能用上传、勾选代替。〔U，2026-10-30〕
10. **岗位库里能找到的岗位，就一定能投。** 投不了（合集页、宣传页、要先选具体岗位）是我们工程的问题，不是用户的问题：不在界面上给岗位打「投不了」的标、不让用户先挑；引擎要能从合集页走到具体岗位的表单，或者岗位库按具体岗位入库。〔U，2026-10-30〕

## 7. 怎么从这份文档推演情景

这份文档的价值在于：给定这些前提，就能推出高概率的真实情景，而不是凭空想象一个「典型用户」。推演时按下面的顺序走：

1. **挑时间点**：处于哪个阶段、离上次打开隔了多久（第 2 节）。
2. **数对象**：这时手上大概有多少份申请、处于什么状态，有几件带期限（第 2、3 节的数量级）。
3. **放外部事件**：这段时间外面来了什么邮件，哪些是重复的、哪些是拒信（第 4 节）。
4. **看他想管多少**：这件事涉及的是目标岗位还是海投，他现在是什么情绪（第 1 节）。
5. **对照立场**：要设计的东西有没有违背第 6 节。

### 7.1 标准情景（设计和评审时拿来走一遍）

**A. 准备期，三周后回来**〔推演〕
- 状态：暑期实习投了 5 家，都没有回音；字节、阿里的提前批快开了。
- 他想要的：知道有什么新变化，顺手补一段实习经历；不想被催。
- 要你的事：零件或一件。

**B. 关键期的一个周二**〔推演，用于投递切面预览〕
- 09:10 说「这 20 个都投了」，其中 3 个是标了星的目标岗位。
- 09:16 20 家都缺证件号码，填一次全部放行。
- 09:48 两个网站要登录；美团的定制版要过目。
- 10:30 九方云来信，在线测评明晚截止。
- 11:05 插进来一句「帮我准备后天百度的面试」。
- 12:20 发现简历项目名有错字：没投的换新版，已投的改不了。
- 14:10 拼多多拒信（只计数）；讯飞笔试通知。

**C. 两天没开，回来**〔推演〕
- 状态：期间来了 1 个面试邀请、2 个笔试或测评、2 封拒信，其余 13 家没有回音。
- 他想要的：先处理最急的那件（今晚截止的测评），其余知道个数就行。

**D. 关键期中途第一次打开**〔推演，冷启动待验证〕
- 状态：已经在官网和平台投了几十家，邮箱里堆着历史通知，有 PDF 简历，还没有任何资料。
- 他想要的：软件把已经投的那些接过去，告诉他现在有什么在等他。

## 8. 未知与改判信号

| 未知 | 为什么重要 | 如果答案是…就要改 |
|---|---|---|
| 学校邮箱能不能连 | 不连邮箱，长程链条整个断掉 | 连不上 → 冷启动必须提供替代的接管方式 |
| 网申确认信的覆盖率 | 决定能不能从邮箱识别「没回音」的申请 | 覆盖率低 → 要靠平台投递页或用户自己的投递表 |
| 用户在什么时段、什么场景用电脑 | 决定提醒时机和单次使用时长 | 主要在手机上处理 → 要重新考虑通知和对外推送 |
| 同时用几个邮箱 | 决定外部通知是否完整 | 普遍多个 → 冷启动要支持连多个 |

## 9. 维护规则

- **只收跨功能的知识**：只对某一个功能成立的结论写进那个功能的规范，不写进这里。
- **每条带等级和日期**：推测被确认后改成 U确认；被推翻的条目保留一行「已推翻：原来认为……，因为……」，不悄悄删掉。
- **用户的纠正最优先**：用户一句「实际上……」可能改写一整节，改完回头检查依赖它的功能规范。
- **保持短**：这份文档每次都要被完整读完，冗余的例子和论证放到功能规范里。
