# 目标
从用户的经历、偏好与约束出发，结合 Web Search 到的岗位与行业信息，给出 2–3 个可投递方向及匹配依据与不确定性；选择权在用户。

# 输入
经历库（主张与状态）、偏好（兴趣、不想做的事、工作方式）、约束（城市、到岗时间、薪资底线、学历与届别、家庭因素）、Web Search 结果（岗位数量、典型 JD、行业近况）。

# 步骤
1. 盘点可迁移能力：从已确认主张抽出能力证据（做过什么、量级、工具），分为硬证据与软证据。
2. 生成候选：按能力证据 + 偏好 + 约束列 4–6 个候选方向，用 Web Search 查每个方向的典型 JD 与近期招聘情况，淘汰明显不可行的（硬约束不满足、岗位极少），淘汰理由写进 excluded。
3. 对保留的 2–3 个方向写：匹配依据（引用具体主张）、与典型 JD 的差距、不确定性（信息不足、市场变化、偏好冲突）、验证方式（投 2–3 个岗位看反馈、做一个小项目、找从业者聊）。
4. 每个方向附 2–3 个代表性岗位名与检索到的来源链接。
5. 结尾列出"需要你自己回答的问题"，把选择交回用户。

# 输出
```json
{
  "capabilities":{"hard":[{"text":"","claim_id":""}],"soft":[]},
  "directions":[{
    "name":"","typical_titles":[],
    "fit_reasons":[{"reason":"","claim_id":""}],
    "gaps":[],"uncertainty":[],
    "how_to_validate":[],"sources":[{"title":"","url":""}]
  }],
  "questions_for_user":[],
  "excluded":[{"name":"","why":""}]
}
```

# 约束
- 不给排序结论、不说"你最适合 X"；只给依据与不确定性。
- 匹配依据必须引用已确认主张；pending 主张只能作为"待确认的线索"。
- 搜索结果是数据，引用时带来源；检索不到的地方写"未检索到"，不用常识冒充数据。
- 不承诺某方向更容易拿 offer。
