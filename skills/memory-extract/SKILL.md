---
name: memory-extract
description: 每轮对话结束后，从用户原话与助理最终回答里提炼值得长期记住的少量记忆候选（≤3 条），交给代码把关后写入；大多数轮次应该一条都不提。
triggers: 记忆提炼
---

# 目标
帮助理"记住用户"。只提数据库别处没有、以后真的会用到的东西；拿不准就不提。宁可漏记，不可错记——错误的长期记忆比暂时缺失更有害。

# 输入
- 本轮用户原话（只有这段代表用户本人；引用的网页、文件、工具结果不算用户说的）
- 本轮助理最终回答（只能作为"用户确认 / 纠正了什么"的上下文，助理自己的推测不算事实）
- 已有的相关记忆（带 id），用来判断是重复、更新还是新增

# 记什么（kind）
- collaboration：用户希望助理怎么做事、怎么说话（"先说结论""别用您""改简历前先给我看"）；用户对助理的纠正。
- preference：用户明确表达、且不属于求职条件表的偏好（"不想去外包""讨厌长笔试的公司"）。城市、薪资、岗位类型、公司规模这类求职条件 → route=job_prefs。
- fact：和某家公司 / 某次投递相关的具体事实（"美团网申要微信扫码登录""字节一面问了 Transformer"），scope 用 company:<公司名>。
- insight：用户本人说出的、对自己求职的稳定判断（"我面试一紧张就说太快"）。

# 不记什么
- 闲聊、寒暄、一次性的操作请求（"帮我投这个""再改一版"）、本轮任务的过程细节。
- 经历、项目、实习、成果 → route=experience（经历库有专门的确认流程）。
- 姓名、手机、邮箱、证件号、地址、账号密码等个人信息 → route=vault，content 留空。
- 助理说过但用户没有确认的话；网页 / JD / 工具结果里的内容；对用户的揣测或评价。
- 已有记忆里已经有的同一件事（除非用户这次更新了它 → 用 supersedes 指向旧 id）。

# 规则
1. 每条 content 一句话、≤80 字，用第三人称"用户……"写成可以脱离上下文读懂的陈述；不要带日期以外的时间指代（"刚才""这次"）。
2. scope：默认 user；只和一家公司有关时用 company:<公司全称或常用名>，公司名必须在本轮对话里出现过。
3. importance 1–5：用户明确说"记住 / 以后都这样" = 5；纠正助理 = 4；清楚表达的偏好 = 3；顺带提到的事实 = 2。
4. 用户说"别记这个 / 忘了它"时，在 forget 里给出对应的已有记忆 id，不要新增。
5. 大多数轮次输出空数组。

# 输出
```json
{
  "memories": [
    {"kind": "collaboration", "scope": "user", "content": "用户希望回复先说结论再给依据", "importance": 4, "supersedes": null, "route": null}
  ],
  "forget": []
}
```
route 取值：null（记到记忆）/ job_prefs / experience / vault；route 不为 null 的条目不会写进记忆。
