# 参考：folio 的 AI 介入方式、harness 与长期记忆 → 对求职助理的借鉴

来源：`/Users/xinlei/Documents/read-aware-internal/folio-archive/modules/folio`（团队内部项目，Bun + Turborepo，React/Tauri 桌面阅读应用 + 单核心 Agent）。本文只记录"它怎么做、我们该拿什么"，不复述源码。

## 一句话判断

folio 的核心不是模型多聪明，而是**用确定性代码把模型围起来**：上下文装配、窗口裁剪、权限闸、确认协议、事件提交全在代码里；模型只做"生成回答、选工具、几条后台 JSON 判断"。记忆系统是"模型提议、代码把关、条件提交"。这两条正是我们产品（提交永远过人、不编造）最需要的骨架。

## 一、AI 介入与 harness：它怎么做

**介入形态（5 种）**
1. 对话内被动回答：每本书一个持久线程 + 全局多线程；输入带阅读游标与选区，输出是分块流（text / thinking / tool-step / reference 卡片 / interaction 确认 / metric）。
2. 阅读中的动作（解释、查词、翻译、章节总结）：不新建第二个 Agent，宿主抓取精确选区后交给同一个会话；工具参数是空对象，模型不能伪造目标文本。
3. 对话外的后台确定性管线（全部用 fast 档模型）：逐轮记忆提炼（每轮 ≤3 条）、滚动摘要（≤150 词）、章节纪要、巩固（衰减/遗忘是纯函数，合并/矛盾/升格由模型提议、代码设闸）、身份整理、书籍分类。串行排队，失败只记日志。
4. 建档访谈：首次使用且无画像时，系统提示"可选地提出访谈"；模型只能给表单的标签，答案由宿主收，整份候选二次确认后原子提交，submissionId 幂等。
5. 一次性推理 `ask`：无线程无记忆无工具，给插件用；schema 结构化输出失败带违例清单重试一次。

**上下文**
- 系统提示按"变化频率从低到高"排节，保住 provider 前缀缓存：角色 → 规则 → 书籍元数据与阅读位置 → 章节纪要 → 画像 → 记忆前 8 条（注明"只是上下文，重要时用工具核实"）→ 滚动摘要。
- 每轮动态内容（阅读游标、选区 grounding、插件上下文）拼进用户消息而不是系统提示；grounding 由代码确定性注入，不指望模型自己去查。
- 裁剪：按用户轮开窗（默认 12 轮，在 user 边界切）→ 旧的大工具结果（>600 字）折成存根 → 轮末释放图片像素；图片每轮 ≤4 张、16 MiB，非视觉模型完全不发 image block。
- "连续性在记忆里不在转录里"：转录只由宿主写；长期连续性靠记忆 + 画像 + 滚动摘要 + 纪要图谱；更早历史只能由模型主动用 `query_conversation` 取；规则明确"过去助手说过的话是同事未经核实的说法"。

**工具层**
- 首轮核心工具 ≤21 个，其余经 `get_host_capabilities` 按需发现、最近保留 12 个，用测试断言数量。
- 按对象合并成工具族（一个公开名 + operation 分支），写入类标 sequential。
- 执行前再次检查可用性（阅读器就绪、选区、隐私开关），不可用抛稳定错误码 `ui/unavailable`；不可用的工具不进 schema。
- **确认协议**：先注册挂起再发布请求；只有 `approve` 才执行；拒绝返回结构化理由，依赖该选择的操作停止、不挑默认值。系统提示规则：破坏性工具必须直接调用由工具自己弹确认，不能先在文字里征求许可；工具没成功就不能声称完成。
- 工具结果不直接进记忆；提炼只看用户文本与最终回答。

**模型层**
- 两档角色 `smart / fast`，Agent 代码里不写死模型名。
- 失败用正则归类（auth / quota / rate-limited / context-overflow / provider / network）带 `retryable`；运行时内断点续跑只在模型失败时保留，重试复用已完成的工具结果，不重复执行有副作用的工具。
- 结构化 JSON 不靠 provider 原生能力：容错抽取 + JSON Schema 子集校验 + 失败重试一次；后台管线解析失败一律当空结果（宁缺勿坏）。
- 推理预算：输入输出 262144 字符、总输出 131072 tokens，结构化重试也计入。

**评测 harness**
- 真实线程 + 内存端口 + 真实模型跑场景；用例声明 `expectation`（answer mustContain / mustNotContain、tools required / forbidden / exactSequence / maxCalls、interactions requiredKinds）+ rubric。
- 规则断言只作诊断；共享四维评分（正确与有据、完整、有用、克制清晰）；模型 judge 只是初评；最终由人或主 Agent 对照原文语义评审并归因（product / assertion / fixture / judge / environment）。
- 回归：每次写 trend 文件打印差值，定义哈希或 thinking 档位变了标 INCOMPARABLE；manifest 记 git 版本与 prompt / 评估器 / fixture 的 SHA-256。
- 真书题库工厂：统一生成游标、注入、语言检查、围栏红线、泄漏词；断言词必须从原文实证。
- 文档明确：模型评测和桌面实测是两类证据，不能互相代替。

**工程护栏**
- `check-swallowed-rejections`：AST 找静默吞错的 catch，必须记日志或写说明。
- 依赖违规基线只能减不能增。
- 能力矩阵 / 责任模型由 TS 数据生成 MD/HTML，禁止手改；集中验收清单带明确停止规则（partial 不自动成为待办、单测与 commit 数不算验收）。
- 诊断三层：本地滚动日志只记 id 与错误文本；按需诊断包；用户预览后才上报。

## 二、长期记忆：它怎么做

**五层结构**：原子记忆（`memories` 表）/ 书内图谱（`chapter_digests`）/ 线程滚动摘要 / 画像（人工确认的 `summary` 与模型派生的 `traits.consolidated` 物理分开）/ 实体身份（`entities` + 别名 + 重定向）。

**记忆条目**：kind 只有 fact / preference / insight / summary；scope 拍平为 `user / global / book:<id>`；字段 importance、evidence_count、pinned、status（active / superseded / forgotten）；软删除保留审计。版本号 `mem1:` = hash(行内容, 最后事件 ID)，条件写防 ABA。

**写入**：事件 + 投影同一事务（`commit_events`），所有专用提交器遵守同一契约；来源有逐轮提炼、显式 `remember`、插件候选、访谈种子；划线笔记不派生记忆。

**整理（空闲每 5 分钟，读集不变则不调模型）**
- 升格：evidence ≥3 或 pinned 才有资格进画像/身份整理；book → user/global 升格需 evidence ≥3，模型提议、代码复核。
- 冲突：模型给 winner/loser，代码校验 id 真实、不在本批触碰集、loser 未 pinned，落成 superseded + winner revised。整批 IMMEDIATE 事务逐行比对 revision，任一行变化整批作废。
- 去重三层：提示词要求"重复就强化"、TS 规范化文本比对、原生同事务查同 scope 同文本。
- 实体：合并用根重定向不成环、原始别名全保留、"同名不等于同一人必须有证据"、新 ID 由代码按 (kind, name, 证据 IDs) 哈希派生、每批 ≤32 决策、大输入二叉归约分页可断点续跑。
- 遗忘：非 pinned 且 30 天未更新 importance ×0.85，低于 0.15 且 evidence <2 标 forgotten(decay)；用户遗忘后自动提炼同文本被压制，只有用户显式 remember 可重建。

**检索**：不用向量库也不用 FTS（FTS 只给批注和正文）；按 scope 过滤 + 关键词匹配（拉丁 ≥4 字、CJK ≥2 字），排序纯词典序 `pinned DESC, importance DESC, updated_at DESC`；系统提示注入"最强的 8 条"；更多靠模型主动 `search_memory` 分页（带 expectedRevision）。为空时要求模型去掉关键词再列一次，不得把"没搜到"说成"没有记忆"；读取失败显示错误不显示空结果。

**上下文包**：带格式版本、配方版本、范围、source-set revision、省略原因（privacy / spoiler / unavailable）的不可变快照，内容版本 `cb1:<sha256>`，上限 512 条 / 1 MiB，超出失败不截断。用于"当时给模型看的是什么"的可复现。

**它自己的两处短板**（我们要避免）：证据/置信度没有进投影（出处只剩事件元数据）；`correct / reject` 两种反馈信号没有任何投影效果。

## 三、对求职助理的借鉴

### 直接照搬
1. **单核心 Agent + scope 线程**：记忆不随线程拆分。我们的"单一对话 + 功能页"映射为 `user` 全局 scope + 对象 scope（`company:<id>` / `application:<id>` / `interview:<id>`）。
2. **工具内确认协议**：先注册挂起再发布；只有 approve 才执行；拒绝/跳过返回结构化理由并停止依赖操作。这正是我们 `action_queue` 的最小内核；把两条系统提示规则原样加进 `assistant-core`：破坏性工具自己弹确认不先在文字里问；没成功的工具调用不能声称完成。
3. **失败归类 + retryable + 运行时断点续跑**：托管浏览器的动作不可重放，重试必须复用已完成的工具结果。
4. **工具面预算**：常驻核心工具 + 按需发现 + 保留最近 N 个 + 测试断言数量。我们 26 个工具已经超过它的首轮上限。
5. **上下文瘦身**：按用户轮开窗、旧工具结果折存根、轮末释放图片；网页快照与截图尤其需要。
6. **事件 + 投影同一事务、可重放、漂移校验**：主张状态每次跃迁要能审计"谁、凭什么从 pending 变 verified"。
7. **条件写**：per-row revision（内容哈希 + 最后事件 ID）、IMMEDIATE 事务比对、冲突后重读再确认。防止用户编辑与后台整理互相覆盖。
8. **人工确认层与模型派生层物理分开**，派生层带 source IDs，来源一变即失效。对应我们 `user_confirmed` 与 `verified / pending` 的边界。
9. **用户删除压制自动重建**：删掉的经历或主张不能被下一次简历解析或对话提炼复活。
10. **提炼保守闸**：每轮 ≤N 条、严格 JSON、区分"用户自述 / 引用材料（JD、公司页）/ 假设"，只有自述能成为经历或偏好；命中已有条目就强化不新建。
11. **评测四类用例**：克制（闲聊不写记忆）、范围隔离、更正后状态检查、敏感信息不复述；断言与 judge 分开计分；trend 差值与 INCOMPARABLE；manifest 哈希溯源。
12. **工程护栏**：`check-swallowed-rejections`、依赖基线只减不增、AGENTS.md 的交付与停止规则。

### 改造后用
1. **建档访谈 → 经历建档**：模型只出标签、宿主收答案、整份候选二次确认、原子提交、submissionId 幂等；但种子不限 4 条，允许单条增量修订，已有画像时不拒绝而是进入"补充"流程。
2. **轮后管线 → 求职提炼**：对象从阅读偏好换成岗位偏好、投递事实、面试反馈；衰减参数按求职周期重调：偏好与约束（期望城市、薪资底线）衰减或提醒复核；经历与证据是事实不衰减；公司档案按 observedAt 过期提示。
3. **剧透围栏 → 输出闸**：改成"未经确认的主张不得进简历 / 对外提交"与"不得编造履历"的负证据比对，违规先重写再兜底。
4. **确定性 grounding 注入**：把当前功能页对象（JD、简历版本、浏览器当前页摘要）确定性地注入本轮。
5. **插件确认的参数快照 → 持久动作队列条目**：批准什么就执行什么、过期、随取消失效；我们已有 `action_queue`，需补"参数快照哈希"与重启后 interrupted 语义。
6. **实体身份**：公司（子公司、改名、中英文名）、面试官、联系人、项目名的别名表与根重定向合并；合并需证据与用户确认。
7. **上下文包 → 投递包 / 面试准备包**：主张 + 证据 + 公司档案 + 省略原因，`cb1` 哈希可复现，事后可对照"当时给模型看的是什么"。
8. **检索排序**：沿用结构化范围 + 关键词 + 词典序；加一项确定性打分"主张对 JD 要求的覆盖度"。
9. **真书题库工厂 → 真实 JD × 简历组合题库**：统一骨架、实证断言词、control 双胞胎。

### 不适用
章节会话与阅读游标、叙事性分类与章节纪要图谱、E2E 多端同步与 HLC 合并、完整插件 Worker 沙箱与资源令牌桶、大型能力矩阵/责任模型治理、BYO 多 provider 与中继双账户。

## 四、我们当前 schema 相对 folio 缺的机制

| # | 缺口 | 后果 | 补法 |
|---|---|---|---|
| 1 | 写入日志与可重放 | 无法审计主张状态跃迁 | 加 `domain_events` 表，所有写走"事件 + 投影同事务" |
| 2 | 整理流水线 | 同一主张多种表述并存；经历时间线矛盾无人裁决 | 空闲整理：去重、冲突 winner/loser + supersededBy、升格门槛 |
| 3 | 强化计数与重要度 | 检索只能按时间排 | claim 加 `evidence_count`、`importance`、`pinned` |
| 4 | 遗忘与压制 | 删掉的内容会被重新提炼 | status 加 forgotten(reason=user) 并压制同文本重建；公司档案加新鲜度 |
| 5 | 反馈闭环 | pin / correct / forget 无路径 | `manage_claim` 工具：inspect → 展示差异 → 确认 → 条件写；`user_confirmed` 只能由这条路径产生 |
| 6 | scope | 跨投递隔离与披露边界无从表达 | claim / preference / company 加 scope；导出敏感字段需显式授权 |
| 7 | per-row revision | 后台整理与用户编辑竞争覆盖 | 行级 revision + 条件写 |
| 8 | 派生层与人工层分离 | 模型生成的优势总结冒充事实 | profile 分 `summary`（人工）与 `derived`（带 source IDs） |
| 9 | 实体身份 | 同一公司多个档案无法安全合并 | company / contact 别名表 + 重定向 |
| 10 | 带版本的上下文快照 | 无法复现简历/求职信依据了什么 | tailored 版本关联 `context_bundle(cb1 hash)` |

我们比 folio 好的一点：证据本来就是一等表。保持主张 → 证据的强外键，并补上证据来源（对话 ID、文件哈希、引文）。

## 五、落地顺序建议

1. **先补骨架**（Phase 1 收尾）：`domain_events` + 条件写 + claim 的 evidence_count / importance / pinned / status 扩展 + `manage_claim` 确认闭环。
2. **再加闸**：确认协议两条规则进 `assistant-core`；输出闸（未确认主张不得进简历）；工具面预算与数量断言。
3. **再做整理**：空闲整理（去重、冲突、升格、遗忘）+ 实体别名合并，全部"模型提议、代码把关、条件提交"。
4. **最后评测**：按 folio 的 expectation + rubric 结构建场景库，先做克制、隔离、更正、不编造四类。
